RISKS:
- Stripe confirm is a stub: order-tracking.tsx confirmCardPayment(clientSecret) is called with no card/Payment Element (comment admits 'minimal flow'), so if Stripe keys are ever configured the Confirm payment button cannot succeed. Today card orders rely on pending → restaurant-side confirmation.
- The 'Payment pending' Stripe box renders for ANY order with status 'pending', including cash orders — a cash customer sees 'Pay with card' + (in prod) 'card payment unavailable' error if they tap it; guests get a raw 'not_signed_in' error since createStripePaymentIntent requires a session.
- Landing CTA fallback: MERCHANT_URL defaults to http://localhost:3004 — if NEXT_PUBLIC_MERCHANT_URL is unset in prod, both 'Start 14 days free' buttons point to localhost. Likewise 'See a live menu' hardcodes /r/coastal-grill/brooklyn (404s if the demo tenant is absent) and the menu hero falls back to a hardcoded Unsplash URL.
- Reorder silently degrades: orders-list.tsx skips combo lines entirely and drops all modifier selections and line notes when rebuilding the cart, so a reorder can differ in contents and price from the original with no warning.
- Reservation page over-promises and has a Thai leftover: success copy says 'We'll send a confirmation to {phone}' but no SMS/email is sent anywhere, and the phone placeholder is '08x-xxx-xxxx' (Thai format) in a US-only product. Page is also orphaned — nothing links to /reserve.
- push-subscriber.tsx queries customers by user_id with .maybeSingle() and no limit — a user with customers rows at 2+ restaurants makes maybeSingle error, silently skipping push registration on every storefront (checkout uses order+limit(1) for the same lookup; the same unguarded pattern is in IssueReportButton and createReservation which additionally filter by branch_id even though customer identity is brand-scoped, so tickets/reservations can get customer_id null on non-home branches).
- Checkout writes email cross-tenant: supabase.from('customers').update({email}).eq('user_id', …) has no branch/restaurant filter, so entering an email at one restaurant overwrites the email on that user's customers rows at every restaurant.
- Tracking progress bar always shows the 'Out for delivery' step — pickup and dine-in orders display a delivery stage they will never reach (status jumps ready → completed).
- Hardcoded pricing in checkout UI: 5% service fee and $3.99 flat delivery fallback (saved address without coords) are client constants; if place-order's formula drifts, the quoted total differs from the charged total.
- datetime-local min uses new Date(...).toISOString().slice(0,16) — min is computed in UTC, so in any non-UTC timezone the browser's minimum selectable schedule time is off by the UTC offset (validation still happens server-side only for the past).
- Swallowed failures: DeliveryChat sendMessage null result is dropped with no user feedback; addresses-view delete/set-default use .catch(() => undefined); checkout's post-order address save is fire-and-forget; middleware resolveDomain catches all errors (a Supabase outage makes every custom domain silently render the Favornoms landing page).
- Cosmetic bug in sign-in-view.tsx line 121: the email-stage subtitle is a JS string containing a literal HTML entity — renders as 'we&apos;ll send you a one-time link' on screen.
- Orders empty-state copy mismatches: signed-in users with zero orders still see 'will appear here once you sign in'.
- ORDER_ERRORS mapping relies on substring matching of edge-fn error text (order-sensitive, e.g. dropoff_other_required vs dropoff_required) — a reworded server error silently falls through to raw message display.
- CCPA do_not_sell cookie and cookie_consent accept/reject are recorded but nothing in the codebase reads them (no analytics is actually gated) — compliance theater to verify before handoff.
- Menu card always renders a star rating icon with item.rating?.toFixed(1) — items with no rating show an empty star + '·' separator artifact.
- OrderTracking hardcodes hasRating={false}; correctness depends entirely on the client-side order_ratings re-check (extra roundtrip per delivered-order view, and if that query fails the modal stays closed by design — a rating can be silently never asked for).

RISKS:
- SCHEMA NOT IN VERSION CONTROL: supabase/migrations/ does not exist in the repo — all 156 migrations live only in the remote DB. A client handoff cannot rebuild the database from the repo. Highest-priority gap; run `supabase db pull` (or dump schema) before handoff.
- Branding storage policy bug: branding_owner_insert/update/delete compare `(storage.foldername(r.name))[1]` — the RESTAURANT'S NAME, not the object path (objects.name) — so the owner_user_id branch never matches; only the staff_members UNION branch grants access. Owners without a staff_members row cannot upload branding. Also the branding bucket has NO file_size_limit and NO MIME allowlist (any authenticated staff can upload arbitrary files of any size to a public bucket).
- Silent dispatch dead-end: orders_after_ready_dispatch and expire_dispatch_offers both `return`/skip silently if private.get_setting('supabase_url'/'service_role_key') is null — deliveries sit in 'dispatching' forever with no error surfaced. Verify both settings exist in the private settings table on any new environment.
- Notification channels are env-gated at the edge fn: email throws 'resend_not_configured' without RESEND_API_KEY (abandoned-cart + gift-card emails), SMS throws 'twilio_not_configured' without Twilio creds, push needs VAPID keys. Outbox rows will accumulate status='failed'; nothing in the DB alerts on this.
- ~15 sensitive RPCs still have EXECUTE granted to anon (admin_edit_order_notes, driver_cancel_delivery, fail_delivery, pay/reject/request_driver_withdrawal, requeue_failed_delivery, mark_delivery_arriving, mark_messages_read, upsert_customer_address, get_delivery_driver_contact...). Spot-checked 4 — all guard with `auth.uid() is null → raise auth_required`, so no open hole, but it's defense-in-depth debt and one future function missing the guard becomes exploitable. Blanket `revoke execute ... from anon` recommended.
- Billing gates read the branches.entitled_through MIRROR, not subscriptions directly — manually flipping a subscription row in SQL without triggering billing_compute makes suspension/expiry tests look broken (documented gotcha, but will bite the client's QA).
- cancel_order / refund does not appear to compensate inventory: stock decrements on order_items INSERT (trigger) but no restock on cancellation was found — cancelled orders permanently consume stock. Verify and decide.
- Penalty bucket wipe: record_driver_penalty DELETEs all driver_penalty_events for the driver when the cooldown trips — penalty history/analytics are unrecoverable by design; reporting on repeat offenders is impossible from this table.
- platform-admin audit trigger swallows its own insert failures (warning only, by design so audits never block merchant repairs) — audit completeness is not guaranteed; failed audit inserts are visible only in Postgres logs.
- billing_expire_tick never expires a subscription whose current_period_end AND trial_ends_at are both NULL — a manually-activated subscription created without a period end stays active forever. Confirm the manual-activation UI always sets period_end.
- Batching flag is per-branch (branches.settings.batch_enabled), not the platform features jsonb — easy to look for the toggle in the wrong place; currently OFF everywhere and never browser-tested end-to-end (P0 pending).
- set_branch_hours is the only SECURITY INVOKER RPC (relies on caller's RLS) — inconsistent with everything else; if staff RLS on branch_hours ever changes, this silently breaks while all definer RPCs keep working.
- Trigger functions (accrue_driver_earnings, tg_billing_gate_*, orders_on_complete_record_tip_split, etc.) have EXECUTE granted to anon/authenticated — not callable via PostgREST (return trigger) so harmless, but grant hygiene noise that will alarm a security audit.
- Quote defaults are hardcoded US values in quote_delivery ($2.49 base, $2/mi, $2.99 min, $9.99 max, 5mi radius, 24 km/h ETA) — fine per-branch override exists, but a new branch with empty settings silently gets these numbers.
- sweep_abandoned_carts uses recipient_type='walkin' with recipient_id=abandoned_cart.id — notify-worker must special-case this or the email join fails; verify one abandoned-cart email actually sends in staging.
